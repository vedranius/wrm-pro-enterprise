# Security policy

## Supported versions

Security fixes go into the **latest release** only. Please upgrade before you report a problem, and include the version you use (`wrm -version`, `/api/version`, or the top bar).

| Version | Supported |
|---|---|
| v14.x | ✔ |
| v13.x and older | ✘ (published under PolyForm terms; see [LICENSE-CHANGE.md](LICENSE-CHANGE.md). The v13.x code and history live in the predecessor repository [`web-browser-RDM-public`](https://github.com/vedranius/web-browser-RDM-public)) |

## Reporting a vulnerability

**Do not open a public issue for security problems.**

- Use GitHub's **private vulnerability reporting**: *Security → Report a vulnerability* in this repository.
- If that is not available, open an issue that says only that you have a security report and asks for a private contact. Do not include details.

Please include:

- the affected version and platform,
- what an attacker can do, and what they need first (no account, guest link, signed-in user, share member, admin…),
- steps to reproduce or a proof of concept,
- if you have them, suggestions for a fix.

You will get an answer as soon as possible, usually within a week. Once a fix is released, the release notes credit you if you want. Please give a reasonable time to release a fix before you publish anything.

**In scope:** the WRM server, web UI and container image in this repository. For example: authentication and 2FA bypass, privilege escalation between users or share roles, access to stored secrets or to other people's session recordings, changing or deleting audit records without detection, cross-site scripting or request forgery, reaching servers or networks you should not reach (the TURN relay, SSH tunnels and jump hosts included — e.g. using another user's jump host or tunnel, or bypassing the tunnel policies), getting the **AI assistant** to run something its mode does not allow (escaping the read-only classifier, the approvals, the automatic-mode limits or the destructive-pattern list, or changing the mode from server output), reading another user's AI transcripts, provider keys reaching the browser, using **AI connections (MCP)** beyond their user, connections, mode, scopes or lifetime (token theft or reuse after revoke or expiry, OAuth flaws such as redirect URI, PKCE or consent bypass, cross-origin calls to `/mcp`), and denial of service with small effort.

**Out of scope:** problems that need an administrator account or access to the server's files, missing HTTPS when the operator did not configure it, social engineering, reports from automated scanners that come without a working attack, and vulnerabilities in the servers you connect to.

## Continuous security checks

Every push and pull request (and a weekly run) checks WRM automatically. The checks are free on GitHub for this public repository; their results are in the pull request and under *Security → Code scanning*.

| Check | What it finds | Where |
|---|---|---|
| **govulncheck** | known vulnerabilities in Go, the standard library and the modules, limited to code WRM calls; fails when one is reachable | `security.yml` |
| **CodeQL** (`security-extended`) | injection, path traversal, unsafe redirects, XSS in the Go server and the JavaScript UI | `codeql.yml` |
| **gosec** | Go security patterns; fails on findings that are not in the reviewed baseline `.github/security/gosec-baseline.json` (`tools/gosec-baseline.js`), and when gosec cannot load the code | `security.yml` |
| **staticcheck** | bugs and deprecated APIs (`remote-manager/staticcheck.conf`) | `security.yml` |
| **gitleaks** | tokens and private keys in the commits of a push or pull request; the whole history weekly (`.gitleaks.toml`) | `security.yml` |
| **actionlint, zizmor** | broken or unsafe workflows: unpinned actions, injection through titles or branch names, broad token permissions, persisted credentials | `security.yml` |
| **Dependency review** | a pull request that adds a dependency with a known vulnerability (moderate or worse) | `security.yml` |
| **Trivy** | vulnerabilities in the Docker image's OS and npm packages; fails on a fixable CRITICAL one | `build.yml` (Docker job) |
| **OpenSSF Scorecard** | the repository's security practices | `scorecard.yml` |
| **Dependabot** | weekly updates of Go modules, GitHub Actions and the Docker base images | `.github/dependabot.yml` |
| **Claude security review** | security problems in the changes of a pull request, with WRM's own checklist (`.github/security/claude-review-instructions.txt`) | `claude-security-review.yml` |
| **Go fuzzing** (nightly) | crashes and hangs in the parsers for uploaded and pasted files: mRemoteNG XML, SSH config, CSV/XLSX inventory, PuTTY `.reg`, WinSCP bookmarks, configuration files, deploy-config YAML (`remote-manager/fuzz_test.go`; the seeds run with every `go test`) | `nightly.yml` |
| **OWASP ZAP** (nightly) | missing headers, cookie flags, information leaks and other passive findings of a running WRM, signed out and as a signed-in administrator; the reports are kept as a workflow artifact | `nightly.yml` |

Rules for the workflows: the token is read-only unless a job uploads release assets, every action is pinned to a full commit SHA (Dependabot updates them), and checkouts do not keep credentials.

The **Claude security review** needs the repository secret `ANTHROPIC_API_KEY` (*Settings → Secrets and variables → Actions*); without it the job is skipped. It is billed per token to that key, so set a monthly spend limit for the key in the Anthropic Console. Because the reviewer reads the pull request's text and code, which an attacker could write, it runs only for pull requests from branches of this repository, never from forks. Keep *Settings → Actions → Fork pull request workflows* at *Require approval for all external contributors*.

Development sessions with Claude Code also run the **wrm-security-review** skill (`.claude/skills/wrm-security-review/`) before every push: the built-in `/security-review`, the same checklist and the same scanners, with the result in the pull request.

**gosec baseline (v12.8.1):** 225 findings were reviewed and accepted. They are paths WRM builds itself (data directory, recordings, Medium runtime, Bitwarden cache, OpenCode install and run directories), commands WRM runs by design with separate arguments (SSH, Docker, ipmitool, service managers, OpenCode — including the v12.8.1 Docker `inspect` call in `ocContainerIP`, whose container name is generated by WRM and passed as a separate argument, without a shell), URLs that users or administrators configure on purpose (Git servers, AI providers, NetBox; WRM can reach whatever its host can reach, so restrict who may add them), TLS verification skipped only where the user chose a self-signed certificate or the certificate is pinned or checked afterwards, and MD5/SHA-1 kept for compatibility (mRemoteNG, TOTP, Git). A new finding must be fixed, or reviewed and added to the baseline with the reason in the pull request. gosec's taint rules (G7xx) are not deterministic (the same code gives a few findings more or less from run to run), so the baseline is made from about 20 runs with Go 1.26.9, the release CI pins: `node tools/gosec-baseline.js run1.json run2.json … --update` keeps each finding with the highest count any run had.

## Signed releases

Every release has `SHA256SUMS.txt` (the SHA-256 of each file) and, since v12.6.21, `SHA256SUMS.txt.sig`: an **ed25519 signature** of that file, made in the release workflow with the project's release key. The signed message is a fixed WRM context, the file name and the file's bytes, so no other signature made with the key can pass as a release signature.

- **Self-update:** with a known release key (built into WRM for this repository, plus the administrator's `update_signing_keys` for a fork), the update refuses a release whose signature is missing or does not verify, before anything is downloaded and run. Without any known key it verifies the SHA-256 only, and the update dialog says *Signature: not checked*. The audit entry `system.update_verified` records the key that signed.
- **By hand:** `wrm -release-verify SHA256SUMS.txt` with `SHA256SUMS.txt.sig` next to it checks the signature and the SHA-256 of every listed file in the same folder. `-release-public-key wrm-ed25519:…` adds a key.
- **SBOM and provenance:** each release has a CycloneDX SBOM (`sbom-vX.Y.Z.cdx.json`) and GitHub build provenance (SLSA, signed with Sigstore). `gh attestation verify <file> --repo vedranius/web-browser-RDM-public` shows the workflow and commit that built a file.
- **The key:** a maintainer creates it once with `wrm -release-keygen release.key` on their own computer. The content of `release.key` goes into the repository secret `RELEASE_SIGNING_KEY`, then the file is kept offline or deleted. The printed public key goes into `builtinReleaseKeys` (`remote-manager/releasesign.go`). A new key is added at the top of that list while releases signed with the old one are still offered. Once a build has a built-in key, the release workflow fails rather than publish an unsigned release.
- **Automatic releases:** a push to `main` whose version is new (the same in `APP_VERSION`, `AppVersion` and the top CHANGELOG section) is tagged by the `Tag new version` job of `build.yml` after every build passed, which then starts the release run on that tag. The job needs `contents: write` and `actions: write` only for itself; nobody has to create releases by hand.

## Security levels

Since v12.6.22 an administrator chooses a **security level**: *Home* (WRM's earlier defaults), *Business* or *Enterprise*. The level is a floor for the settings in `levelRules` (`remote-manager/security_level.go`): HTTPS for sign-in, required 2FA, password length, session lifetime and idle time, lockout, registration, host-key policy, server-side keys, secret export, guest links and their lifetime, AI full access, audit and recording with their retention. The full table is in the [README](README.md#security-levels-and-posture).

- **Chosen at install or later:** on the first-run screen, with `wrm -security-level` / `WRM_INITIAL_SECURITY_LEVEL` (applied once) or forced with `WRM_SECURITY_LEVEL` (locked in the UI), or in *Admin panel → Security*.
- **Raised, never loosened:** applying a level only raises settings that are weaker than it; stronger settings stay. An environment variable that forces a weaker value is shown as a problem, not overridden.
- **Preview first:** the preview lists changes, blockers (for example HTTPS while the administrator's own browser uses plain HTTP, which would lock them out) and the people affected. *Sign out other sessions* makes new session limits and required 2FA apply at once.
- **Deviations need a reason:** a setting may stay below the level only with a written reason. Who recorded it and when is stored in `security_deviations` and audited (`security.deviation`, `security.deviation_removed`, `security.level_changed`, `security.level_enforced`).
- **HTTPS for sign-in** (`require_https`): password sign-in, registration and the 2FA step are refused over plain HTTP, except from localhost, so a password never travels unencrypted. Behind a reverse proxy, set `TRUST_PROXY` so WRM sees the original scheme.
- **Security posture:** *Admin panel → Security* checks the installation against the level (transport, every rule, 2FA set up, where the encryption key lives, `WRM_ALLOW_ANY_ORIGIN`, guest links without expiry, signed updates, current version, audit hash chain) and exports the result as JSON or a printable report. It contains no secrets.

## Roles, step-up and break-glass

Since v12.6.23 (`remote-manager/roles.go`, `teams.go`):

- **Least privilege by role:** a *Security auditor* reads the audit log, terminal sessions and recordings, file transfers and the security posture (`GET` only, `requireAuditRead`) and is refused connections (`authorizeConnection`), the AI assistant and AI connections. *Operators* pass only the policies set to `operators`. Who-policies can also name teams (`teams:<names>`); team names are checked against existing teams, and a team named in a policy cannot be deleted or renamed, so a policy never silently points at nothing.
- **Step-up re-authentication** (`require_step_up`, required by the Business and Enterprise levels): changing policies, the security level or roles, creating administrators or auditors, disabling or deleting users, break-glass changes, password and 2FA resets, revealing a stored credential password or a connection's saved login, exporting a private key and exporting connections with secrets need a password (and TOTP or recovery code) confirmation no older than `step_up_minutes`. The confirmation is bound to the sign-in session (`auth_sessions.step_up_at`), wrong passwords count toward the sign-in rate limit, and every attempt is audited (`auth.step_up`, `auth.step_up_failed`). A stolen session cookie alone therefore cannot change security settings once the window has passed.
- **Break-glass administrator** (`users.break_glass`): a local emergency account that must use 2FA (its sessions end until 2FA is set up), may be limited to `break_glass_ips`, and whose every sign-in is audited (`auth.break_glass_login`) and notified to all other administrators.
- **Deprovisioning:** deleting a user can hand their connections, folders, credentials, SSH keys, shares and proxies to another active, non-auditor account in one transaction (`handOver`, audited `admin.user_handover`). Disabling a user ends their sign-in sessions, terminals, AI sessions and AI connections.

## Directory sign-in (OIDC)

Since v12.6.24 (`remote-manager/oidc.go`, `oidc_jwt.go`):

- **Protocol:** authorization code flow with PKCE (S256), a random `state` that is used once, expires after 10 minutes and must match a cookie set in the browser that started the sign-in (so a sign-in link cannot be completed in someone else's browser), and a `nonce` checked in the ID token. ID tokens are verified with the provider's published keys (RSA ≥ 2048 bits or ECDSA P-256/384/521); unsigned and shared-secret (HS*) tokens are refused, and issuer, audience, `azp`, expiry and issue time are checked. Provider addresses must be HTTPS (plain HTTP only on loopback), including every endpoint the discovery document names.
- **Identity:** accounts are found only by the immutable directory ID (`tid` + `oid` for Entra, otherwise `iss` + `sub`). Names and e-mail addresses are never used to match an existing account; a new account whose preferred name is taken gets a different name. Existing accounts are linked only by their signed-in owner after a fresh confirmation (password and 2FA, or an already linked directory account; asked even when `require_step_up` is off), so a stolen session alone cannot add the attacker's directory account and then pass step-up with it. The provider must confirm the person, and an existing link is never replaced silently.
- **Least privilege from the directory:** accounts are created only for people a rule matches, and every sign-in re-applies the role and SSO teams; people no rule matches are refused and their sessions end. The last active administrator is never demoted by a sign-in. Break-glass accounts stay local.
- **Deprovisioning:** signed-in directory users are revalidated with their refresh token every `oidc_revalidate_minutes`; a refused refresh, a token no rule matches, or no successful check for `oidc_unverified_hours` ends their sign-in sessions, terminals, tunnels, rooms and AI sessions.
- **Secrets:** the client secret and refresh tokens are encrypted at rest (`encryptValue`) and never sent to the browser or written to the audit log. *Test sign-in* shows only the ID token's claims to the administrator.
- **Local passwords:** `local_login = break_glass` (required by the Enterprise level while a provider is enabled) leaves password sign-in and self-registration only to break-glass administrators, so a person disabled in the directory cannot fall back to a local password.
- **Audit:** provider changes, accounts created from the directory, links, role syncs, ended access, test sign-ins and every refused directory sign-in with its reason.

## LDAP / Active Directory and SCIM

Since v12.6.25 (`remote-manager/ldap.go`, `ldap_proto.go`, `scim.go`, `directory.go`):

- **Transport:** LDAP connections always use TLS (LDAPS, or StartTLS before any bind), TLS 1.2 or newer, with the certificate and host name checked against the system store or the directory's CA certificate. There is no setting to skip the check.
- **Passwords:** the person's password is checked by binding as them and is never stored or logged. Empty passwords are refused before the bind (an empty simple bind is an anonymous bind on most servers). Failed directory sign-ins count towards the IP lockout. The service account password is encrypted at rest, never sent to the browser, and never sent to a changed server address: changing the address requires the password again (the same applies to an OIDC provider's client secret when its issuer changes).
- **Injection:** every value in a filter is escaped (RFC 4515), and administrator filters are compiled and validated before use.
- **Identity:** accounts are found by the directory's immutable ID (`objectGUID` or the configured attribute), never by name. Disabled, locked and expired accounts are refused at sign-in and at every check.
- **Deprovisioning:** linked accounts are checked every `ldap_sync_minutes`; SCIM disables accounts at once. Any route that stops an account (administrator, OIDC revalidation, LDAP check, SCIM) runs `endUserAccess`: sign-in sessions, terminals, tunnels, rooms, AI sessions and AI connections (MCP tokens) end.
- **SCIM tokens:** random 256-bit bearer tokens with the prefix `wrm_scim_`, shown once and stored only as SHA-256; rotation and revocation need step-up. A client sees and changes only the accounts and groups it created, never local accounts, never the last active administrator's role or state, and never a team an administrator made. Requests are limited to 600 a minute per address and 1 MB each.
- **Linking:** linking a directory account to an existing WRM account needs a fresh confirmation (even with step-up off), the directory password, and an account that is not break-glass. A SCIM account is linked to an OIDC identity only when its `externalId` equals the token's `oid` or `sub` and it has no directory link yet.
- **Audit:** directory changes, accounts created, links, checks that ended access, test sign-ins, refused sign-ins with their reason, and every SCIM change.

## SIEM export, alerts and lockdown

Since v12.6.26 (`remote-manager/siem.go`, `alerts.go`, `lockdown.go`):

- **Delivery:** every audit entry goes to each SIEM destination in order and at least once; each destination keeps its own position in the audit log, so an outage loses nothing while the entry is kept. Events carry the audit hash chain (`hash.prev`, `hash.this`), so the SIEM can show that no entry was removed or changed.
- **Transport:** syslog only over TLS (RFC 5425), HTTPS destinations only over HTTPS (plain HTTP only on loopback), TLS 1.2 or newer, certificates checked against the system store or a CA certificate pasted per destination; redirects are not followed. A syslog client certificate's private key is stored as the secret.
- **Secrets:** HEC tokens, API keys, Sentinel client secrets and private keys are encrypted at rest, never sent to the browser, and never sent to a changed address or kind (the secret must be entered again). Destinations are changed only by administrators with step-up.
- **File output:** an absolute path with a `.jsonl`, `.json` or `.log` name in an existing folder, never through a symbolic link, written with mode 0600 and rotated at 100 MB.
- **Alerts:** repeated failed sign-ins, break-glass sign-ins, new administrators, revealed or exported secrets, AI full-access approvals and the audit or a SIEM export turned off raise `security.alert` entries and notify administrators. Security events (`security.*`) are recorded even with `audit_enabled` off, and turning the audit or an export off raises an alert itself.
- **Stop user** disables an account and ends its sessions, terminals, rooms, tunnels, AI sessions and AI connections at once (step-up).
- **Lockdown** lets only break-glass administrators (2FA, optional `break_glass_ips`) sign in or keep a session, switches AI and AI connections off and refuses shares. It needs a fresh confirmation and a reason, cannot be turned on while there is no break-glass administrator, can only be ended in the UI by a break-glass administrator, and can be set on the host (`wrm -lockdown on`) or forced (`WRM_LOCKDOWN=1`) when the UI is not trusted.

## Hardening checklist

WRM is secure by default in most respects. For production and company use, also check the items below. The admin panel (*Overview*) warns about several of them.

**Transport and exposure**

- [ ] Serve WRM over **HTTPS** only: a reverse proxy with a real certificate, `HTTPS_CERT_FILE` + `HTTPS_KEY_FILE`, or at least `HTTPS_SELF_SIGNED=1`. Without HTTPS, passwords and terminal traffic between browser and WRM are not encrypted, and browsers block the microphone.
- [ ] Behind a reverse proxy, bind WRM to localhost (`LISTEN_ADDR=127.0.0.1:8080`), pass the `Host` header through, and set `WRM_TRUST_PROXY=1`. Set `WRM_TRUST_PROXY` **only** when clients cannot reach WRM directly.
- [ ] Do not set `WRM_ALLOW_ANY_ORIGIN=1`.
- [ ] Put WRM behind a VPN or an IP allow-list when only internal users need it.
- [ ] Firewall: expose only the HTTPS port. Open the TURN ports (3478 UDP/TCP and the relay range) only if you use voice calls across networks. Otherwise set `turn_enabled=0`, or set `voice_enabled=0` to turn off voice entirely.

**Keys and data**

- [ ] **Back up the encryption key** (`<DB_PATH>.key`, or your `ENCRYPTION_KEY` / `ENCRYPTION_KEY_FILE`) **separately** from database backups. Someone who has both can decrypt the stored secrets.
- [ ] Keep the database, the key file and the self-signed certificate readable only by the WRM service user. WRM creates them with mode `0600`.
- [ ] Run WRM as an unprivileged user. `-install-service` writes a systemd unit with `User=`, `NoNewPrivileges`, `ProtectSystem=strict` (the data and binary folders writable), `ProtectHome=read-only` and `PrivateTmp`; the service's settings file `<data dir>/wrm.env` is mode `0600` (it may hold `ENCRYPTION_KEY`). The Docker image runs as an unprivileged user; provide the encryption key as a Docker secret (`ENCRYPTION_KEY_FILE`) instead of keeping it only in the data volume.

**Updates**

- [ ] The one-click update installs only a release file whose **SHA-256 matches the release's `SHA256SUMS.txt`** and which answers `-version` with the release version; it is refused otherwise. Both come from the same GitHub release, so the check protects against broken or swapped downloads, not against a compromised release repository: keep `update_repo` at the official repository (or your own mirror) and `self_update` at `admins` (or `off` with `WRM_SELF_UPDATE=off`). Every step is audited (`system.update_*`).
- [ ] The update check sends no user data (only the repository path and a fixed User-Agent). Turn it off in air-gapped networks with `WRM_UPDATE_CHECK=off`.
- [ ] Only administrators may write to the binary's folder: a newer `wrm-pro-v…` file copied there is started by the service on its next start (after a `-version` check).

**Accounts**

- [ ] Keep **self-registration closed** (the default) and create accounts in *Admin panel → Users*.
- [ ] Set **`require_2fa`** to `admins` or `all`.
- [ ] Use a sensible `password_min_length` (12 or more), and the lockout (`login_max_failures`) and session lifetime policies (`session_idle_hours`, `session_max_days`) your company requires.
- [ ] Disable accounts of people who leave (*Disable* signs them out everywhere at once) and review *Admin panel → Users* regularly.

**Connections and sharing**

- [ ] Keep `host_key_policy` at `tofu` or `strict`. **Never** use `off` in production.
- [ ] Keep `allow_server_keys=0`, so only administrators can use key files stored on the WRM server.
- [ ] Set `allow_secret_export=0` if users must not export their stored passwords and keys.
- [ ] Set `allow_link_shares=0` if guests without an account must not join shares.
- [ ] Prefer **Members only** shares with the lowest role that is enough (*Viewer* to look at files, *Observer* for calls and watching). Give shares an expiry date.

**Terminal features and live status**

- [ ] Decide about **broadcast input** (`broadcast_enabled`). It only types into the user's own open terminals, but one command reaches many servers; dangerous commands ask first. Every start and stop is in the audit log (`terminal.broadcast`).
- [ ] Review **shared snippets** (administrators publish them for everybody) like any runbook. Run-on-connect snippets come from the connection's owner and are audited (`terminal.auto_run`).
- [ ] **Folder bookmarks** marked as shared are visible (read-only) to everybody who uses your connections through a share: do not put secrets in their names, paths or notes.
- [ ] **Live status** opens a TCP connection to every monitored host:port once per interval (no login). Tell the teams who watch those servers, add the WRM server to fail2ban `ignoreip` where *aggressive* filters are used, and keep `status_jump_checks` off unless logins to the jump hosts every round are acceptable. The Workboard's *Server load* addon logs in over SSH (at most once a minute per server while visible) for servers without Monitoring; turn `workboard_ssh_metrics` off where that is not wanted.

**SSH keys & credentials vault**

- [ ] Give shared credentials a **host list** (`Only for hosts`): a password is sent to the server at login, so without one a colleague could send it to a server of their own. With a host list, the people it is shared with can only use matching hosts and jump hosts.
- [ ] Prefer keys (deploy them with WRM) over shared passwords, and **revoke** keys of people who leave — *Who has access* shows what is left on a server.
- [ ] Keep `allow_secret_export` off if users should not be able to export private keys or show vault passwords (administrators always can; every export is audited).
- [ ] Use **read-only** GitLab / GitHub / Gitea tokens for the Git workspace (e.g. GitLab `read_api` + `read_repository`, a GitHub fine-grained token with *Contents: read* (and *Metadata: read* for the repository activity), a Gitea token with `read:repository`). They are stored encrypted and never returned, but anyone with the WRM account can use them to read the repositories. Git checks only read files on servers; limit them with `git_checks` or hide the workspace with `git_enabled`.
- [ ] Anyone allowed Git checks can **open any file** of an installation folder in the Git workspace (the SSH login's read rights apply; protected files are shown from the server, never from Git; symlinks are not followed and paths cannot leave the installation). Each opened file is audited (`git.file_viewed`); limit who may do this with `git_checks`.
- [ ] Git **runs** (update, upgrade, rollback, restart) write on servers with the SSH login of the connection: keep the policies `git_update`, `git_upgrade`, `git_rollback` and `git_restart` at *admins* (the default) unless others need them. Production installations (tag `env:prod`) need the typed server name; every run is audited per installation (`git.update`, `git.upgrade`, `git.rollback`, `git.restart`, `git.stamp`). Restarts use `sudo -n` only when the SSH user is allowed it without a password — grant just the `systemctl restart` / `supervisorctl` commands it needs.
- [ ] Git **Simple mode** derives environments from what the checker found; this is read-only until someone starts a run (same permissions, locks and audit as before). Saving them to the catalog (`git.env_adopted`) needs the `git_update` policy. WRM reads each server's hostname with a fixed `hostname` command over the existing SSH login and caches it; no new privileged path.
- [ ] Git **installs and transfers** create directories, write per-host configuration and (opt-in) unit files on the target: keep `git_install` and `git_transfer` at *admins* (the default). Typed per-host values are never stored with a run; vault values are read on the WRM side and only for servers the credential's host list allows. Overwriting an existing installation and production targets need the typed server name; replaced files are backed up first. Audit `git.install` / `git.transfer`.
- [ ] Git **environment deploys** take a **lock** on each destination: `mkdir <state>/.lock` (atomic) with an owner file holding the deploy id, the WRM user, the WRM host name and the server's time — no secrets. A deploy removes only a lock whose owner file names its own deploy id. A **stale** lock (older than max(30 minutes, the transfer timeout) by the server's clock) is removed only after an explicit confirmation, by one remote command that checks the owner id and the age again (audited as `git.lock_removed`); remove it only when you know no deploy is running there. The state directory (`<path>/.deploy-bak` by default) holds backups of replaced files — keep it out of public web roots (the access doctor warns about paths that look like one).
- [ ] The remote commands of environment deploys are fixed POSIX scripts; file names travel on **stdin**, never in the command line, and every path is shell-quoted. A rollback never acts through a symlink on the server and moves files aside instead of deleting them. **`post_deploy`** is a command from the catalog that runs in the app directory with the SSH login's rights — only when it is ticked for a run (and shown before it runs); treat editing a service's environments like editing a deploy script. Dry runs take no lock and write nothing.
- [ ] The Git **activity, deploy history and "what is where"** views only read: the provider API with the source's read token (the token stays on the server; the browser gets commit metadata and web links), and `history.jsonl` / `state.json` / `VERSION.md` over SSH under the `git_checks` policy. Their **CSV exports** contain author names, servers and paths — treat them like the audit log; values a spreadsheet would run as a formula (`=`, `+`, `-`, `@`, tab, CR at the start) are prefixed with `'`.
- [ ] Git **write tokens** (for .gitignore merge requests only) are optional: give them only the scope needed to push a branch and open a merge / pull request, and keep `git_gitignore_mr` at *admins*. WRM writes to a Git server only on an explicit, confirmed request (audit `git.gitignore_mr`).
- [ ] Git **webhooks** (`/api/hooks/git/<id>`) take no session: the hook ID and its secret authenticate them (GitHub HMAC, GitLab token, or the generic token / timestamped HMAC). Prefer HMAC signatures, keep the secret in the CI's secret store, renew it when it leaks (*New secret*), and watch `git.webhook_rejected` in the audit log. Webhooks only start checks (read-only on servers).
- [ ] **CI pipeline** tokens (Jenkins API token, GitLab trigger token) and artifact feed headers are stored encrypted and sent only to their configured host (no redirects to another host). A CI-deployed update goes through the same policies and confirmations as a normal one.
- [ ] Use a **read-only** NetBox token for inventory imports; a remembered token is stored encrypted, but anyone with the WRM account can use it to read NetBox.
- [ ] Set a rotation reminder on shared passwords and rotate them when a colleague leaves; check the audit log for `credential.rotation_incomplete`.

**Out-of-band management & serial ports**

- [ ] Use BMC accounts with the least role that does the job (*Operator* for power actions) and a vault credential with a host list for them.
- [ ] Keep `serial_ports` at `admins` (or `off`): serial ports belong to the WRM machine.
- [ ] Watch `bmc.power` events; power actions and consoles are limited to the connection's owner.

**Quick connect, notes & network tools**

- [ ] Set `network_tools` to `admins` (or `off`) if users should not probe networks from the WRM server or from their servers; every run is audited as `nettool.run` (tool, target, source).
- [ ] Notes are stored in clear text in the database (like connection names): keep passwords in the vault, not in notes.
- [ ] Quick connections are audited as `connection.quick` and removed 24 hours after their last use; they use the same host key checks as saved connections.

**Remote desktop (RDP / VNC / Telnet)**

- [ ] Run guacd only on the WRM machine (or in WRM's network namespace) and keep it bound to `127.0.0.1`: guacd has no authentication of its own, so anyone who reaches port 4822 can open connections through it.
- [ ] Prefer **NLA** or **TLS** security for RDP and turn off *Accept the server certificate* where servers have proper certificates.
- [ ] Turn off the remote clipboard (connection option) on servers where copying data out must not be possible; sessions are recorded like terminals.
- [ ] Turn remote desktops off (`desktop_enabled=0`) if nobody needs them.

**SSH tunnels and jump hosts**

- [ ] Decide who may use tunnels: `tunnel_users=admins`, or `tunnels_enabled=0` if nobody needs them (`WRM_TUNNELS_ENABLED=0`). Tunnels reach whatever the SSH servers reach; they are as powerful as the SSH accounts behind them.
- [ ] Keep `tunnel_bind_any=0` and `tunnel_remote_forward=admins` (the defaults). A tunnel on `0.0.0.0` or a network address is **not protected by WRM sign-in**: anyone who reaches that port uses the tunnel. If an administrator opens one, restrict it with the host firewall.
- [ ] When WRM runs on a shared server, remember that `127.0.0.1` tunnel ports are reachable by **every local user and process** of that server. Run WRM on a dedicated host or container, or limit tunnels to administrators.
- [ ] Set `tunnel_idle_minutes` so forgotten manual tunnels close themselves, and review running tunnels in *Admin panel → Overview*.
- [ ] On the bastions, allow only the forwarding you need (`AllowTcpForwarding`, `PermitOpen`, `GatewayPorts no`), as you would for OpenSSH clients.
- [ ] Watch for `tunnel.start`, `tunnel.error`, `tunnel.configured` and `web.open` events in the audit log.

**Proxies**

- [ ] Decide who may define proxies (`proxies=admins` or `off`); everybody may use proxies shared with them. A proxy reaches whatever its network reaches, like a jump host.
- [ ] SOCKS and HTTP proxy logins travel in plain text to the proxy. Prefer proxies on trusted networks, reach them through a jump host (the hop is encrypted), and give shared proxies their own accounts. WRM never sends a shared proxy's password through a grantee's own jump hosts.
- [ ] A "WRM SOCKS tunnel" proxy uses its owner's SSH login and cannot be shared. Review running tunnels (*Admin panel → Overview*) and the `tunnel.*` and `proxy.*` events.
- [ ] In Docker, a proxy on the host (`host.docker.internal`) should listen only on the Docker bridge, not on every interface.
- [ ] WRM refuses a proxy address on its own machine that is a running SSH tunnel of another user; tunnels on `0.0.0.0` (administrators, `tunnel_bind_any`) are still reachable from the network, see *SSH tunnels* below.

**Notifications**

- [ ] Channel secrets (bot tokens, webhook URLs, SMTP passwords) are encrypted at rest and never returned; treat a leaked webhook URL like a password and replace it.
- [ ] Use STARTTLS or TLS for e-mail; WRM does not send an SMTP password over a plain connection to another machine.
- [ ] Notification texts contain connection names, hosts and error messages: send them only to channels the recipients may read. With *Users may enter their own recipient* users can send their own notifications to any address of that kind.
- [ ] Sign webhooks (`X-WRM-Signature`, HMAC-SHA256) and check the signature on the receiving side. Watch `admin.notify_channel_*` events.

**Audit trail and session recording**

- [ ] Keep the audit log on (`audit_enabled`, the default). Run *Admin panel → Audit log → 🔏 Verify integrity* regularly, and after any incident. A broken chain means that someone changed the database directly.
- [ ] Decide about **session recording** (on by default). Tell your users that terminal sessions are recorded (in many countries this is required), and set `recording_retention_days` to match your retention and privacy rules.
- [ ] Turn on keystroke recording (`session_recording_input`) only if you need it. Typing at password prompts is masked, but other secrets typed on the command line would be recorded.
- [ ] Recordings may contain sensitive output (configuration files, logs). Keep the recordings folder (`WRM_RECORDINGS_DIR`, mode `0700`, files `0600`) on an encrypted disk, include it in protected backups, and give administrator rights only to people who may see them. Every view and download of a recording is audited.

Keep `ai_personal_keys=off` if users must not send server data to their own accounts.

- [ ] Give the SSH logins the assistant uses the least privilege: it acts with the connection's login (and `sudo -n` only where that login may). - [ ] Keep `ai_allow_power=off` unless reboots through the assistant are needed (then each one needs an approval).

## Service inspection, hierarchy and remote previews (v12.4.0)

Service configuration inspection requires ownership of the registered installation/SSH connection and `git_checks`. Paths cannot escape the installation through symlinks; files, entries and output have caps. Secrets are masked by conservative key-name checks and existing credential/token/URL redaction. Config contents are read on demand and are not stored in the database. Runtime logs are redacted before caching; unstructured remote logs should still avoid writing secrets in arbitrary prose. Runtime commands read state as the SSH account, without automatic sudo or restart. Optional HTTP/TCP probes run from that server, have short timeouts, reject URL credentials, follow no redirects and verify TLS.

Remote previews require `files_read` on every metadata/range/content request, including shared viewer roles. Unknown binary types are refused; HTML/SVG and source formats render as text. Inline responses use `nosniff` and no-store; non-PDF previews have a sandbox CSP, while PDFs use the browser native viewer with a restrictive document CSP. Text previews are bounded; media ranges seek on the remote server. Preview actions never execute terminal selections or interpolate them into shell commands. Preview access is audited as `file.preview`.

Folder parents must belong to the same user; hierarchy mutations are serialized and reject cycles/excess depth. Shared folder recursion is scoped to the owner. Sharing a parent folder includes existing and future descendant folders: check the folder tree before moving a connection into a shared subtree. Jump/proxy defaults apply only to the immediate folder. Deleting a parent reparents its children, preserving their connections.

## Showing and copying a connection's saved login (v13.10.0)

- *Show saved login* and *Copy password* (`POST /api/connections/{id}/secret`) are for the **owner of the connection** only. They need the owner's WRM password, or the directory password of an LDAP / Active Directory account (checked by binding as the user); accounts that sign in only through an identity provider need a fresh step-up through it. Wrong passwords count towards the sign-in rate limit and are audited (`connection.secret_denied`).
- A vault credential is shown only to **its owner**: a grantee who logs in with a shared credential still never sees its password. Key files of the WRM server are named, never read for the browser.
- The administrator's *Allow export of passwords & keys* policy (`allow_secret_export`) applies, as does *Confirm dangerous actions (step-up)*. Every reveal is audited (`connection.secret_revealed`, with `purpose` show or copy) and raises the *secret revealed* alert when it is on.
- The browser receives the secret only in the answer to that request; copying goes to the clipboard without showing the password in a notification. A password you copied stays in the operating system's clipboard until something else is copied.

## Logs, log search and AI chats (v13.5.0)

- Log discovery, search and line reads run over the connection's own SSH account, without sudo, as read-only commands (`systemctl list-units`, `grep`, `find`, `sed -n`, `tail -c`, `journalctl`). Every path in those commands is shell-quoted and comes from the server's log settings or from the metadata just read; search and line reads accept only paths and journal units the last discovery returned (`logSearchable`), so a request cannot name `/etc/shadow`. Regex searches use `grep -E` with a size limit; output is capped (about 900 KB per read) and the commands have time limits.
- Log settings are stored encrypted per connection; only the connection's owner can change them or start a discovery. Shared users can read the logs their role allows.
- The log assistant is always read-only; a purpose limits the tools the model is offered and `CallTool` refuses any other tool. The file assistant edits only through `edit_file` / `write_file`, so every change is a diff that waits for approval in the ask mode, like in the terminal panel.
- The AI sessions view (v13.8.0) lists, exports and continues only the signed-in user's own sessions (another user's session answers 404); exports are the stored, redacted transcript and are audited (`ai.session_export`). Saved sessions outlive `ai_transcript_retention_days` while `ai_keep_saved_sessions` is on; turn it off to enforce the retention for everybody. Personal AI settings hold only IDs and names, never keys; a personal default provider is used only while the policies still offer it. An MCP approval given after the AI app stopped waiting runs the reviewed call at once (`ai_mcp_later_approval` = `run`), with the plan that was shown and checked again against the current mode and policies just before it runs; set `repeat` to require the AI to repeat it.
- Chat titles are generated with no tools from the first question and answer (both already redacted); continuing a chat sends the earlier, redacted transcript of the same user to the provider again. Thinking summaries are redacted and stored like other transcript entries.
- The editor checks the file on the server before it writes and asks before overwriting a newer version.

## AI assistant: threat model

The built-in assistant (v12.0.0) lets a language model act on a server. WRM treats the model as an **untrusted, possibly manipulated actor** and puts the decisions on the server:

- **No shell for the model.** The model can only call WRM's fixed tools. Each call becomes an action (read a file, run a command, edit a file) that the **permission engine** evaluates on the server before anything runs: the session's mode, the read-only classifier, the automatic-mode allow / deny lists and limits, the always-blocked destructive patterns and the unreadable sensitive files. The browser only shows approvals and passes the user's decision back; the engine does not depend on the panel (the MCP integration of v12.1.0 uses the same engine).
- **Prompt injection from server output.** Logs, files and command output can contain text written by anyone (an attacker who can write a log line, a web request, a file in a shared directory). Tool results are given to the model as **untrusted data**, framed and labelled as such, and the system prompt tells the model never to follow instructions in them. This reduces but cannot eliminate manipulation, so it is not what WRM relies on: **only the user can change the mode** (through the authenticated API, never through a tool), there is no tool that changes permissions, unknown tools are refused, and every action is evaluated by the engine regardless of why the model asked for it. In *ask* mode a manipulated model can only *propose* a change, which the user sees exactly; in *auto* mode it can only do what the user's allow list permits, within the limits, and never anything on the destructive list.
- **Read-only means read-only.** The classifier is an allowlist: commands it does not know, and anything with redirections, command or process substitution, here-documents, subshells, background jobs or variables, count as changes. Wrappers (`sudo -n`, `timeout`, `xargs`) are unwrapped and the inner command is checked. Sensitive files (password hashes, private keys, cloud credentials, process environments) are refused also through wildcards and symlinks (`read_file` resolves the real path first). A file the login can read through other means (e.g. a custom script) is outside what any classifier can know: give the SSH login only the rights it needs.
- **Destructive patterns** are checked on the parsed command and again on the raw text with quotes removed, so a pattern hidden in `sh -c "…"` or `eval` is still caught; they are refused in every mode, also after an approval and after the user edits a command. The list is maintained in `ai_destructive.go` and every rule has a test.
- **Approvals.** A pending approval shows the exact command or a unified diff; only the session's user decides; an edited command or content is evaluated again; an unanswered approval is denied after `ai_approval_timeout_seconds`; a file is written only if it is unchanged since the diff was made. Every request, decision (approved, denied, edited, timed out, cancelled), who and when, is audited.
- **Data leaving to providers.** Everything the assistant reads — command output, file contents, the OS description, and the connection notes if the user opts in — is sent to the chosen provider. With `ai_redact_output` (default on) secrets are replaced before sending (the patterns of the audit redaction — password, secret, token, credential, private key, passphrase … — plus private key blocks, `Authorization` headers, passwords in URLs, AWS / GitHub / GitLab / Slack / OpenAI / Anthropic / Google keys, JWTs, password hashes). Redaction is best effort; administrators choose which providers and models are allowed, and personal keys are off by default. Stored WRM secrets (connection passwords, keys, vault entries) are never given to the model.
- **Keys.** Provider keys, AWS secrets and service account keys are encrypted at rest (`encryptValue`), never returned by the API (only *is set* flags), never written to the audit log, and scrubbed from provider error messages.
- **Kill switch.** A session can be stopped (the running request and command are cancelled) or ended by its user; administrators end one session, all sessions of a user, or all sessions, turn the assistant off per user, or turn on `ai_kill_switch`, which ends everything and blocks new sessions until it is turned off. Pending approvals of an ended session are cancelled.
- **Recording.** Transcripts are redacted, kept for `ai_transcript_retention_days` and visible to the session's user and administrators; every session is also recorded like a terminal session.

## OpenCode and helper models (v12.6.11)

- **Helper models** get only the text the assistant passes to `delegate_task`, redacted with the same rules as tool output and limited to `ai_delegate_max_kb`. They have no tools. Models that may use prompts for training (OpenCode Zen's documented free models, and any model without published terms) are excluded unless `ai_delegate_training` allows them; the default lets each user opt in for themselves, and the choice is audited. Every delegation is audited with model and size.
- **OpenCode binary.** WRM installs OpenCode only after an administrator confirms. It downloads the platform package named for the host from the configured registry (HTTPS only), compares the tarball's sha512 with the registry's `dist.integrity`, extracts only `package/bin/opencode[.exe]` (no scripts run, no other paths written) and runs `--version` before use. A registry mirror you do not trust is a supply-chain risk; `ai_opencode_path` lets you supply a binary you vetted yourself.
- **OpenCode agents are contained by WRM.** Each agent is a separate process on `127.0.0.1` with a minimal environment (no `WRM_*` variables, `HOME` in its own session folder), project configuration, plugins, skills and auto-update disabled, and OpenCode's own shell, file, web, LSP and question tools disabled in the configuration WRM writes; permission requests are refused. Its only way to a server is WRM's MCP server, through a session-scoped AI connection (kind `opencode`) that is accepted **only on the loopback listener WRM opened for it**, never on `/mcp` from the network, and is revoked when the session ends. So the permission engine, approvals, full-access rules, redaction and audit apply to it exactly as to any AI connection. Treat the OpenCode process like the provider it talks to: it sees the tool results it receives.
- **Leftovers.** Stopping WRM stops every agent (its process group) and removes its folder; after a crash the next start stops a leftover agent recorded in its pid file (Linux) and removes the folders.

## OpenCode in a Docker sandbox (v12.6.19)

- **Off by default.** Only an administrator turns it on (`ai_opencode_sandbox` = `admins` or `all`), and each user ticks it per session.
- **Every action asks.** OpenCode's shell, file changes and web fetches inside the sandbox are WRM approvals that show the exact command, diff or URL. They cannot be edited and are never approved automatically: not by automatic mode, not by full access, not by approve-later. Other OpenCode permissions are refused. Reads inside the sandbox folder do not ask.
- **The container is the boundary, not the approval alone.** It runs as WRM's own user ID with all capabilities dropped, `no-new-privileges`, a read-only root file system, memory, CPU and process limits, and only the session's folder and the OpenCode binary (read-only) mounted. Nothing of the WRM host's files, Docker socket or WRM's database is inside. OpenCode's API port is published on `127.0.0.1` and protected by a per-session password. If WRM runs as root, the container's user is root too, still without capabilities; run WRM as its own user.
- **What the sandbox can reach.** The container has outbound network access like any container (web fetches ask; a shell command could still open connections, so read commands before approving them). The provider key and the session's AI-connection token are in its environment, so an approved command could print them: they are the same credentials the agent already uses, the token is limited to this session's server, scopes and mode and dies with the session. WRM's MCP listener for sandboxes binds to the Docker bridge gateway on Linux; other containers on that bridge can connect to it, but every request needs a valid token. A local AI provider on the host's loopback address is forwarded only to the session's container (by its IP address).
- **Servers stay behind WRM.** The sandbox holds no SSH keys or connection data; the agent acts on servers only through WRM's tools, with WRM's approvals.
- **Leftovers.** Containers carry a label per WRM installation; they are removed when the session ends, when WRM stops, and on the next start after a crash.

## AI desktop apps (MCP): threat model

From v12.1.0 an AI app (Claude, ChatGPT or any MCP client) can act on servers through WRM's MCP endpoint (`/mcp`). The model and the app are outside WRM's control, so WRM treats both like the built-in assistant's model: **untrusted**, possibly manipulated, and limited by decisions made on the server.

- **Same engine, same limits.** Every MCP tool call becomes an AI session call (`aiSession.CallTool`): the read-only classifier, the destructive patterns (refused in every mode, after approvals and edits), the approvals, the automatic-mode limits, the mode rules, unreadable sensitive files, redaction of output and the audit. On top of that, the **scopes** of the AI connection decide which tools exist at all; without `run_with_approval` only read-only commands run, without `edit_file_with_approval` files are never written. MCP sessions cannot be driven or re-moded through the panel's API.
- **Approve later (v12.6.1).** An approval that times out, or that the app declines or stops waiting for, stays pending in WRM for an hour; approving it there records a one-time permission for exactly that call (tool and command, or file and content hash) in the same session, used up on the next identical call and expiring after an hour. A denial in WRM is final, and nothing else is pre-approved.
- **Full access (v12.6.2, modes v12.6.3).** Off by default (`ai_full_access`). When an administrator turns it on, `ai_full_access_mode` decides where it applies: every AI session (`all`, the default, so one switch affects every user's AI panel and AI connections), AI connections a user gives the `full_access` scope (`connection`), or users who turn it on for their own sessions (`user`, `users.ai_full_access`, audited as `mcp.full_access`). `ai_full_access_blocked` = `deny` (v12.6.4) keeps the administrator's `ai_blocked_commands` refused even then. There the engine turns every refusal except the read-only mode and missing scopes into an approval: the destructive patterns, `ai_blocked_commands`, deny lists, power commands, protected paths and secret files are then only as safe as the user's decision on each request. They are never automatic, and the approval names the rule. Keep it off where users should not be able to approve such commands; it is re-checked at every call.
- **"Allow everything" (v12.6.1).** An AI connection in automatic mode may allow `*` and `/**` with no time or action limit (`until_grant`, policy `ai_auto_until_grant`, default on). Its sessions then run every command on the connection's servers without asking until the connection expires or is revoked; the destructive patterns, `ai_blocked_commands`, the deny lists, unreadable sensitive files, unparseable commands and power commands still refuse or ask, and the connection never reaches other servers. Turn the policy off where every change must stay within a time and action limit.
- **Token theft.** Tokens are 256-bit random values with a recognisable prefix (`wrm_pat_`, `wrm_oat_`), stored only as SHA-256 and shown once. Each is bound to one user, chosen connections (the user's own SSH connections), one mode, scopes and an **expiry** (default 7 days, at most the policy maximum, by default 30 days); there are no refresh tokens. A stolen token gives at most that, until it expires or is revoked — the owner revokes it in one click (the top-bar indicator or *Settings → AI connections*), administrators revoke any or all, and revoking, expiry, the `ai_mcp` policy, disabling the account, the per-user AI block and the kill switch end its sessions at once. Tokens are accepted only in the `Authorization` header (never in URLs) and the WRM session cookie is never accepted by `/mcp`. MCP session IDs are bound to the token that created them. Failed token checks are audited (`mcp.auth_failed`, with the first 12 hex characters of the presented token's SHA-256 only, never part of the token itself).
- **Confused deputy.** WRM acts with the SSH logins of the user's connections, so it must not act for anyone else: a token only reaches the connections the user chose when creating it (and still owns); an OAuth client gets nothing by registering — it only gets a code after the **user signs in to WRM** (with 2FA) and approves on WRM's own consent page, which names the app and the address it returns to, and where the **user** picks connections, mode, scopes and lifetime (the app's requested scopes are only a suggestion, never more than the policy allows). Dynamic client registration is open (as MCP clients need it) but rate-limited, client names are shown as untrusted text, and unused registrations are deleted after a day.
- **OAuth redirect URIs.** Registered redirect URIs must match the administrators' allowlist (`ai_mcp_redirect_uris`: https, or http on loopback only; no user info or fragments; a wildcard can never reach into the host name). The authorization request must use one of the client's registered URIs exactly; otherwise WRM shows an error page and redirects nowhere. Codes are single-use, expire after five minutes, are bound to the client, the redirect URI and the PKCE challenge; **PKCE with S256 is required** (`plain` is refused); a failed PKCE check consumes the code (`mcp.pkce_failed`), and a reused code revokes the token issued from it. Responses carry `iss` (RFC 9207). The consent page cannot be framed (`X-Frame-Options: DENY`) and its answer needs WRM's CSRF protection.
- **Prompt injection.** Logs, files and command output are framed as untrusted data, but WRM does not rely on the model ignoring them: there is no tool that changes the mode, the scopes, the connections or the lifetime; unknown tools are refused and audited (`mcp.tool_refused`); extra arguments are ignored; nothing in a tool result changes what the token may do. A manipulated app can at most ask for changes — which the user sees exactly in the approval — within the scopes the user gave.
- **Approvals.** Approvals appear on WRM's own page (card with the exact command, diff or transfer, *Approve*, *Deny*, *Edit*) and, if the client supports it and `ai_mcp_elicitation` is on, as an MCP elicitation in the app. An elicitation answer is trusted as the user's answer through the app (audited with `via: mcp`); turn the policy off if only WRM's page may approve. Edits are only possible in WRM and are evaluated again. Unanswered approvals are denied after the timeout.
- **Origin checks and CORS.** `/mcp`, `/oauth/register`, `/oauth/token` and `/oauth/revoke` refuse requests whose `Origin` is neither WRM itself nor listed in `ai_mcp_allowed_origins` (protection against DNS rebinding and cross-site requests, audited as `mcp.origin_refused`); CORS headers are sent only for those origins and never allow credentials. The metadata documents under `/.well-known/` are public. Requests without an `Origin` (desktop apps, hosted connectors' servers, the stdio bridge) are authenticated by their token alone.
- **Transport.** Tokens and tool output travel between the app and WRM: use HTTPS. The stdio bridge talks HTTPS to WRM (`-ca-file` for a private CA); it writes only protocol messages to stdout.
- **Plugin bridge and setup script (v13.13.0).** The Claude plugin and the *All AI apps at once* script run WRM's Node.js bridge on the user's computer. Its `wrm_connect` sign-in is an ordinary OAuth client of WRM: dynamic registration with a loopback redirect `http://127.0.0.1:<random port>/callback` (allowed by the default `ai_mcp_redirect_uris`; remove the loopback patterns there to forbid it), PKCE S256, a random `state` checked on the callback, a one-shot listener on 127.0.0.1 that closes after the answer or 15 minutes, and the normal consent dialog where the user chooses servers, mode, scopes and lifetime. The token never passes through the chat or the model: it is written to `~/.wrm/mcp.json` with mode 0600 in a directory with mode 0700 (on Windows the user profile's permissions apply), and it is a revocable OAuth AI connection like any other. Anyone who can read that file as the user can use the access until it expires or is revoked, the same as an AI app's own configuration with a token. The setup script contains the WRM address and the bridge, never a token; it copies every config file it edits to `<file>.wrm-backup-<time>` first. Over plain HTTP on a LAN the token travels unencrypted, as with any token; prefer HTTPS.
- **Limits.** MCP request bodies are limited (4 MB), sessions per user and AI connections per user are limited, and transfers have their own size limit (`ai_mcp_transfer_max_mb`).

## Medium deploy-config from Git, build user and default engine (v12.9.1)

deploy-config Git actions run only against the repository in the user's own `DEPLOY_CONFIG_REPO` preference and only through a WRM Git source that serves it; reads use the source's read token and commits its write token, and neither token reaches the browser (the repository URL shown is redacted). WRM's copy lives in the user's private Medium directory and is replaced atomically: a pulled head is written and validated in a temporary directory first, and a head whose configuration does not load is never applied. A push validates the whole configuration, refuses when a changed file moved on Git since the pull (no forced ref updates on GitHub), and writes only the fixed deploy-config file names. Pull, push and stop need the `medium_native` policy, like the editor, and are audited with the project, branch, commit and file names, never the content.

`medium_build_user` runs WRM-host builds as an unprivileged account. WRM refuses root, accounts in the root group and accounts that can read the database, its `-wal`/`-shm` files, the encryption key or `<DB>.medium` by their permission bits, and it refuses to run the build as the WRM account silently when the account cannot be used. The build gets its own directory handed to that account and a clean environment without WRM's variables. The build runs in a subdirectory of a WRM-owned directory it cannot change, and `source_dir` is read back only when no component on its way is a symbolic link, so the build cannot point the read-back at other files of the host. When the build ends, WRM takes the directory back (owner and no group/other write, directory before its contents) before reading the result, so a process the build left behind cannot swap files, and a regular file with several links that the build account does not own is refused, so a hard link cannot make WRM read and deploy a file the account could not read itself. This limits what a build command can read on the WRM host; it is not a sandbox against the network or other files that account can read, so build commands are still for trusted operators.

With `medium_default_engine=native`, projects nobody chose an engine for are deployed by WRM for users allowed by `medium_native`; everyone else keeps the original tool. The original tool's runtime is no longer needed for that path, which removes the Docker runtime and its Python dependencies from the attack surface when it is not imported.

## Medium file details and deploy-config editor (v12.9.0)

File details show a changed file of the user's **own** finished plan only (another user's run is `404`), and only paths that are changes of that plan; the server side is read through the user's linked connection, and a link or directory there is described, not followed. The content shown is what the user's connection can already read; opening it is audited without the content. The line-ending hash runs `tr -d '\r' | sha256sum` with names fed on stdin, never in the command line. The deploy-config editor writes only the user's own configuration directory, only the fixed file names (`servers.yaml`, `environments.yaml`, `projects/<name>.yaml`), never through a link, and only when the whole configuration loads; it needs the `medium_native` policy because the configuration decides where deployments go and which `post_deploy` commands run. Every save is audited (`git.medium_config_edit`) without the file's content.

## Medium native deployments (v12.7.0)

The native engine changes servers through the deploying user's own WRM connections only; it never uses another user's connection or a separate SSH profile. Switching a project to it, deploying, rolling back and releasing a lock need the `medium_native` policy (default `admins`), and with step-up on a fresh confirmation; environments with `confirm` need their name typed, and `allowed_refs` and the environment's `servers` list are enforced. A deployment is bound to the comparison the user reviewed (revision) and is compared again under the lock, so a server or config that changed in between gets nothing written. Every remote script quotes its paths and takes JSON through stdin. Paths read back from a server's state (backup manifests, history) are checked to be relative without `..` before a rollback uses them, symlinks on the way are refused, and the browser only gets history entries' counts, never their path lists. `post_deploy` runs what the deploy-config says, with the account's login shell on the server: like the rest of Medium, it is for trusted operators. Audit entries name the project, environment, deployment ID, servers and outcome, never file contents.

## Original Medium runtime and Bitwarden (v12.4.3)

Medium source ZIPs are executable code and require administrator import with explicit confirmation. ZIPs reject traversal, links, devices, duplicates and decompression/entry limits. The original app listens on localhost with a per-process random bridge secret; the proxy does not forward WRM cookies/authorization. Every proxy request rechecks session and Medium/Git policies. Native action requests additionally check update/install/rollback policy and same-origin origin/fetch metadata, including the original no-referrer form case. The bridge allows framing only within WRM. Native runtime preferences are encrypted and credential/command values are masked when retrieved. SSH/config/source files remain private mode-restricted files and must be protected in backups.

**Medium must be limited to trusted operators.** Original config editing, local builds and deployment commands can execute with the WRM OS account's permissions. Private directories/processes do not sandbox code or provide isolation against a malicious trusted operator. Review the original source before import and provide only required OS permissions and native credentials. Native engine locks/plans/history remain separate from Simple/Advanced. Direct network reachability from the runtime is required.

Bitwarden uses the official CLI for vault encryption/authentication and an isolated profile per WRM account. Master passwords, API secrets and session keys are supplied in subprocess environment variables rather than command arguments; an optional one-time MFA code uses the CLI's required code argument. Unlock keys stay in memory and expire after inactivity, WRM logout/restart or explicit lock/logout. The CLI's profile, including account tokens, is sealed with WRM AES-GCM between commands. During a command a mode-0600 plaintext profile exists, and a crash may leave it until startup recovery; filesystem/OS access to the WRM account remains privileged. Preserve the matching WRM encryption key when backing up profile data.

The browser sees only native SSH item IDs, labels and fingerprints; the private key is retrieved and parsed server-side during authentication and is not copied into the connection database. Permission checks apply to item references and SSH/SFTP protocols. Lock does not terminate existing SSH sessions; it blocks future private-key retrieval. CLI responses/errors and master/session secrets are never included in audit details; generic errors and bounded output avoid accidental CLI disclosure. Live cloud login remains dependent on official CLI/account/MFA compatibility and network access.

Configuration profile references are statically parsed, masked and encrypted; Python/source is not executed. Live checks preserve existing owner/policy/path/symlink boundaries and explicit caps. Folder reorder transactions reject foreign anchors, cycles and excessive depth. Public fixtures use generic names; private supplied archives and runtime state are excluded from Git and Docker build context.

## File edit history and SSH certificates (v13.14.0)

- **File edit history** (`file_edits`). Editor saves (`POST /api/remote/upload?…&edit=1`, also in shares) and approved AI file changes are recorded with user, client IP, connection, host, path, source, session and SHA-256 before and after. The unified diff is computed on the WRM server from the content WRM read and wrote (the browser cannot supply it), passed through `redactText` and then encrypted with the WRM key. Files over `file_edit_max_kb` and binary files are recorded without a diff. The table has the same append-only triggers as the audit log and is purged only by the retention job (`audit_retention_days`). Only administrators and auditors (`requireAuditRead`) can list it; opening a diff and exporting CSV (with formula-injection quoting) are audited. Masking is pattern-based: a secret that does not look like one can still appear in a diff, so treat the history like the files themselves, or turn it off with `file_edit_history = 0`.
- **SSH user certificates.** WRM uses a certificate only for the key it was issued for (public keys compared byte for byte) and only user certificates; a certificate saved with a key-store key is validated when saved. Expired certificates are skipped, never sent. Key files and their `-cert.pub` neighbours on the WRM server are read only for connections that may use key files (administrators by default). The certificate is public data; the private key stays encrypted (key store) or on disk (key files) as before. opkssh certificates are short-lived by design: renewing them is `opkssh login` as the user WRM runs as.
- **Git checks.** Files the catalog does not track and log files are no longer fetched from the Git provider or compared, so checks read less data from servers and repositories.

## Addon web requests and secrets (v13.11.0)

- **One network path.** An apiVersion 2 panel still has `connect-src 'none'`; the `http` capability lets it ask WRM, which sends the request from the WRM server. Review an addon's origins on the permission sheet like any other outbound access of the server.
- **Allowlist and approval.** Only origins, paths (exact or `*` prefix, no `..`) and methods in `addon.json`, and only after an administrator approved the origins (`addon_http_grants`, audited). Personal addons never approve themselves. An update that adds an origin, method, path or secret waits for approval again. The policy `addon_http` limits who may use such addons.
- **SSRF.** WRM resolves the host, refuses loopback, unspecified, private (RFC 1918, ULA), link-local (including cloud metadata `169.254.169.254`), CGNAT, multicast, broadcast and reserved addresses (IPv6 forms carrying an IPv4 address, NAT64 and 6to4, are judged by that address), and connects to exactly the checked address (no DNS rebinding); no HTTP proxy from the environment is used. A private address is reachable only for an origin the administrator explicitly marked as private network; plain `http://` needs the same mark. Redirects (3 at most) are re-checked; `E_HTTP_BLOCKED` and `E_HTTP_REDIRECT` refusals are audited.
- **Headers.** Only `Accept`, `Content-Type` and `Range` come from the panel (no `Host`, `Cookie`, `Authorization` or hop-by-hop headers); there is no cookie jar; only a whitelist of response headers reaches the panel. TLS 1.2 or newer with normal certificate checks.
- **Secrets** (`addon_secrets`) are encrypted with the WRM key, at most 4 KB, set by an administrator (shared instance) or the owner (private instance), with an optional per-user override in shared instances. They are never returned by the API or given to the panel (which only sees whether one is set), are sent only to the origin of the request and removed on a redirect to another origin, and are audited by name, never by value. They are deleted with their instance.
- **Limits.** 256 KB request, 8 MB response, 10 s, 120 requests a minute and 20 concurrent per instance, coalescing of identical GET/HEAD within 2 s. The request log (`addon_http_log`) keeps method, origin, path, status, size, duration and code, not bodies, query strings or secrets.
